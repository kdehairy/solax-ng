Derived flags per inverterType (re-derived from SolaXCloud 7.7.1's `invAdres`/flow-page helpers; these aren't fields
in `Data`/`Information` themselves, they're how the official app decides what to show/hide for a given inverterType):

hasBattery = ![4, 6, 7, 8, 16, 18, 22, 26, 41, 43, 44, 100, 101, 104, 105].includes(inverterType)
  These types never have a battery, regardless of what `BatteryCapacity`/`BAT_Power`/etc. in `Data2.txt` decode to
  (their template values are just left at 0). Don't rely on `BAT_Power == 0` alone to detect "no battery" - it's
  ambiguous with "battery present but idle".

hasPV = ![9, 41].includes(inverterType)
  Types 9 (x1ac) and 41 (x1IESA) are pure AC-coupled/battery-only inverters with no PV/DC input at all.

isPvOnly (battery not actually installed on this specific unit, even though the model supports one) only applies to
inverterType in [19, 20, 21, 47]: read bit 0 of `InverterConfigStatus` (see `Data2.txt`, decoded via `hextobtye`) -
if set, no battery is wired up on this particular installation. For every other inverterType this isn't checked;
whatever `hasBattery` says above is assumed to always hold.

isEps (EPS/backup mode active) is not simply `RunMode == 7` for `Data2.txt`-style (`getPub2`) inverters - the actual
thresholds the app uses are:
  inverterType in [64, 69]: isEps = RunMode == 5 || RunMode == 6
  all other Data2.txt types: isEps = RunMode == 6 || RunMode == 7
  (`Data1.txt`-style (`getPub1`) inverters, i.e. types 3, 4, 8: isEps = RunMode == 7, unchanged)
Given how many operating-mode values each inverterType's `RunMode` table has grown to (TOU-x/R-n variants etc, see
below), matching on a mode name containing "EPS" is not reliable - use these numeric thresholds instead.

Generator input / third-party or AC-coupled-solar meter fields (`GenPower`, `GenEnergy`, `solarInverterPower`,
`solarInverterEnergy`, `TotalThirdDevicePower`, `TotalThirdDeviceYield` in `Data2.txt`) are only ever populated by the
app for inverterType in [19, 20, 21, 47, 64, 69] - for every other type these fields should be treated as not
present/meaningless even if `Data2.txt`'s generic template happens to decode some value for them.
